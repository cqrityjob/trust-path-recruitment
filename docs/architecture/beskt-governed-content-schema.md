# BESKT PR 2 — governed method content: schema decisions

**Status:** Schema only; ready for review. No candidate runtime, no UI, no hosted apply, no pilot.

**Depends on:** PR #217 (`docs/architecture/beskt-recruitment-method-discovery.md`, the normative contract). This note records the additive decisions PR 2 makes inside that contract; it changes nothing in it.

**Migration:** `supabase/migrations/20261108090000_beskt_governed_method_content.sql`
**Rollback:** `supabase/rollback/20261108090000_beskt_governed_method_content_rollback.sql`
**Suite:** `supabase/tests/beskt_governed_content_test.sql`
**Guard / controls:** `scripts/beskt-governed-content-check.ts`, `scripts/negative-controls/beskt-governed-content-controls.ts`

## 1. One identity, two spines

`scp_interview_packs` stays the stable identity of every governed interview package. It gains an additive `pack_kind` (`role_interview` | `beskt_method`, constrained text, default and backfill `role_interview`). `role_id` becomes conditionally nullable under a database invariant:

```text
role_interview  =>  role_id IS NOT NULL
beskt_method    =>  role_id IS NULL
```

A BESKT method is justified by versioned role-exposure profiles, not by one canonical `scp_roles` row, so no fake generic role is inserted.

The role-interview version spine (`scp_interview_pack_versions`, competency mappings, 0–4 anchors) is closed to any other kind by trigger, and the five old-flow functions (`scp_iv_case_start_basis`, `scp_iv_startable_pack_versions`, `scp_iv_create_case`, `scp_interview_pack_validate`, `scp_interview_create_version`) are re-created with their exact signatures plus an explicit `pack_kind = 'role_interview'` scope. No RPC name is overloaded. The role-interview content hash is not touched, so every recorded review hash stays checkable.

## 2. Why the tables are `beskt_*` and not `scp_*`

PR 1 requires `ENABLE` **and** `FORCE ROW LEVEL SECURITY` on every new exposed BESKT table. The Security Competency domain suite asserts that no `scp_*` table carries FORCE RLS (a documented trust-boundary decision for that domain). Both are right for their own domain, so BESKT carries its own prefix, as the Passport domain (`sp_*`) does with its own FORCE-RLS tables.

## 4. Governance

- **Hash:** core `sha256` over the text of a typed canonical jsonb document (`beskt_canonical_content`, schema `beskt_canonical_content_v2`): one named array per governed table, every value under its own named key, explicit JSON nulls, arrays sorted, aggregates ordered on stable keys. No delimiter can move content between fields or rows, so two different field/row splits of the same characters hash differently; lifecycle columns excluded. `beskt_canonical_content` and `beskt_method_content_hash` are internal (service_role only).
- **Validator:** `beskt_method_validate(version, require_reviews)`; content completeness at submission, completeness plus all five gates at the current hash **in the current review cycle** inside the publishing transaction. Every submission opens a new `review_cycle`; a rejection returns the version to draft and ends the cycle, so after re-submission all five gates need fresh approvals even if not one byte changed.
- **Gates:** `personnel_security`, `senior_hr`, `recruitment`, `employment_privacy_legal`, `data_protection`; the generic reviewer role is never enough — `beskt_record_review` and the row trigger both require an active grant in `beskt_governance_grants` for exactly that gate (`BESKT_GATE_NOT_GRANTED`), so a revoked, expired, not-yet-valid or wrong-gate grant records nothing, and neither does a service-role writer; reviewer ≠ author, one gate per reviewer per hash, publisher ≠ author, reviews, events and grants append-only for every caller.
- **One open version:** `beskt_create_method_version` takes the per-method advisory lock _before_ the open-version check, and the unique index `beskt_method_versions_one_open_idx` on `(pack_id, open_slot)` refuses a second open version at the table. `open_slot` is a generated column: `'open'` while the version is draft or in_review, NULL from published onward, so NULLs never collide and any number of closed versions may coexist. Two columns on purpose — `pack_id` alone is never unique (a method has many historical versions), so PostgREST and `supabase gen types` cannot infer a one-to-one relation between a method and its versions. `scripts/db-test.sh` proves the invariant with two real sessions in flight.
- **Child writes serialise against publication:** `beskt_guard_child_row` locks the owning version row(s) `FOR SHARE` — in id order when a re-parent names two — _before_ it reads the status, and publication takes `FOR UPDATE` before it hashes. So either the child commits first and publication is refused with a stale hash, or publication commits first and the child is refused as frozen. The published bytes always hash to exactly the approved stored hash. `scripts/db-test.sh` races both orders with two real sessions.
- **Exposure profiles never couple:** a prompt probes only an item of its own profile and a routing rule connects only items of one profile (`BESKT_CROSS_PROFILE_REFERENCE` in the child guard, `PROMPT_CROSS_PROFILE` / `ROUTE_CROSS_PROFILE` in the validator); the resolver neither fires a cross-profile rule nor lets one hide an item.
- **Owning keys are immutable:** every parent key of every child family (`method_version_id`; `section_id`/`exposure_profile_id` on items; `exposure_profile_id`/`item_id` on prompts; source/target/option on routing rules; `item_id` on options) is refused on UPDATE (`BESKT_PARENT_IMMUTABLE`), and the child guard checks the OLD owner as well as the NEW one, so a child of a published, suspended or retired version can never be moved under a draft — not even by service_role.
- **PEACE Evaluation:** a fixed stage (`evaluation`) addressed to the interviewer only, bound to the required `interviewer_self_review` prompt kind; it is a governed reflective step and carries no candidate score, verdict, rating or grade.
- **No scoring through content:** `beskt_text_instructs_scoring(text)` reads the VALUES of every item wording and purpose, every prompt wording and every evidence-anchor component for instructions to score, rate, grade, rank, judge suitability, pass/fail, recommend or hire — in the Swedish and English the product uses (`Rate the candidate's suitability from 1 to 5`, `Betygsätt kandidatens lämplighet på en skala 1–5`, `Award points for each example`, `Godkänd eller underkänd?`). The validator blocks publication with `ITEM_INSTRUCTS_SCORING`, `PROMPT_INSTRUCTS_SCORING` or `ANCHOR_INSTRUCTS_SCORING`. Ordinary interview wording (`What did you do at that point?`) is not flagged.
- **Routing reads shown sources and moves forward:** `beskt_resolve_item_sequence` fires a rule only while its source item is currently shown in evaluation order, so an answer supplied for a hidden or skipped item is ignored deterministically and can neither reveal nor hide anything downstream. A rule whose target does not come after its source in the governed order (section order, item order, item key) is refused at write time (`BESKT_ROUTE_BACKWARD`) and blocks publication if a row is forced past the guard (`ROUTE_TARGET_BEFORE_SOURCE`); no cycle is representable.
- **Mutations:** narrow RPCs only; actor from `auth.uid()`, operation id, SHA-256 request hash, replay answered before compare-and-swap, expected revision required where content can race, event and receipt in the same transaction. No client writer exists for any child table.
- **Read contract (`release_scope = synthetic_internal_only`):** `beskt_published_method` / `beskt_readable_published_versions` / `beskt_resolve_item_sequence` answer governance readers (platform content roles, platform admins) and explicit internal-QA grantees (`internal_qa` in `beskt_governance_grants`) only. Internal QA reads published recruitment-support content whose every profile and item lies within its access classes (never `authorised_security_function`); a document is refused whole, never returned in part. Candidates, ordinary and suspended employer members, roleless users and anon read nothing. Nothing is startable.
- **The identity table:** the Phase 1 editor INSERT/UPDATE policies on `scp_interview_packs` are scoped to `pack_kind = 'role_interview'`; a BESKT identity is created only by `beskt_create_method` and its slug, names and purpose are immutable outside the governed contract (`BESKT_IDENTITY_IMMUTABLE`, trigger, every caller). `listRolePacks()` lists role packs only (`role_id IS NOT NULL`), and the generated Supabase types carry `pack_kind`, the nullable `role_id`, the thirteen tables and the RPCs — a compatibility repair, not application use of BESKT.
- **Rollback:** `supabase/rollback/20261108090000_…_rollback.sql` first refuses if any catalogue object outside the domain depends on it — a foreign key, view, rule, trigger, policy, a function that calls a BESKT function, or a function whose signature names a BESKT row type — or if any version is published. Then it drops child-first in an explicit order without CASCADE, restores the Phase 1 identity policies before dropping `pack_kind`, and restores the five role-interview functions verbatim. It runs in one transaction (`psql -1`), so a refusal drops nothing; `scripts/db-test.sh` plants an outside view and a row-type function and proves both refusals leave the schema untouched.

## 5. What PR 2 does not do

No candidate assignment, notice, response, answer, case link, session, observation, correction, assessor, panel, report, AI generation, application-status change, hosted apply, Lovable publish or real data. No method content is seeded; the suite plants clearly synthetic content inside its own transaction. Candidate preparation begins in PR 3.
