# Security Work AI: proposed provider decision

Status on 2026-09-24: **recommendation for an explicitly approved synthetic pilot; not activated, no live provider request performed, model quality and application latency unverified.** The development agent does not determine the product provider.

## Concrete recommendation

Keep the existing Anthropic Messages API adapter and evaluate **`claude-sonnet-5`** first, using its default adaptive thinking, the pinned Security Work 1.1 task/prompt/policy and the six-case SV/EN dataset. The current official model page lists this exact ID as active, released June 30, 2026, with retirement no sooner than June 30, 2027. Anthropic describes its relative latency as fast; that is a vendor category, not a measurement of this application. [Model specifications](https://platform.claude.com/docs/en/models/sonnet-5/overview).

This is an engineering choice for the first evaluation: the existing adapter already provides bounded output, citation checks, durable application job fences and human-only report approval. Changing providers before evaluating it would add integration work without evidence of better Security Work analysis. A passing JSON response cannot establish that Sonnet 5 is suitable; the human rubric below remains the release decision. Opus 5.5 is a possible separately approved comparison if the first candidate fails the rubric; it is currently listed at twice Sonnet 5's token price and moderate relative latency. [Current model comparison](https://platform.claude.com/docs/en/models/overview).

The dateless Sonnet 5 ID is a fixed snapshot under Anthropic's 4.6-and-later versioning policy, not an evergreen `latest` alias. Serving infrastructure can still change; record the evaluation date and rerun quality checks when behavior changes. The adapter's authenticated model preflight must resolve the exact ID before sending source text. **Availability in the owner's actual API account is still unverified.** [ID/version policy](https://platform.claude.com/docs/en/about-claude/models/model-ids-and-versions).

## Cost and latency envelope

Current standard Sonnet 5 prices are **USD 2 per million input tokens and USD 10 per million output tokens**. For illustration, 20,000 input plus 5,000 output tokens is USD 0.09 before taxes or contract adjustments. This is arithmetic, not an observed bill. The new tokenizer and actual output length affect the token count; no caching/batch discount is assumed. [Official pricing](https://platform.claude.com/docs/en/about-claude/pricing).

Proposed pilot: **12 one-shot requests** (six cases × SV/EN), at most **8,192 output tokens**, **60 seconds per attempt**, and **USD 3 total approved reservation**. The runner computes a deliberately conservative byte-per-token input reservation plus output cap before any network request and refuses an insufficient budget. The current dataset reserves **1,218,132 micro-USD (USD 1.218132)**: for each request, `(UTF-8 request bytes + 2,048 framing allowance) × 2 + 8,192 output tokens × 10`, summed across twelve requests. The executable plan includes this computed value and is authoritative as prompts change. Record observed total request latency and usage per case, then review p50/p95, timeout rate and actual provider billing. None of those measurements exists yet.

The adapter does not automatically retry. A timeout or ambiguous outcome retains its reservation; the app database permits only one dispatch fence per immutable input. The standalone synthetic runner additionally requires one owner-named durable ledger and refuses to replay any existing claim, including a crash or failed response. Its reservation is an application-side estimate, not a contractual provider spending cap. Configure a separate Console workspace/key spend limit as a second boundary.

## Adapter changes prepared for the pilot

The 1.1 prompt asks for decision-relevant follow-ups with reasons, currentness checks against a server-pinned reference time, method-faithful reasoning, supported controls and actions without invented people or assignments. The immutable reservation's method definition is supplied alongside the source text. Title, publisher and dates come only from its exact immutable source IDs through workspace-scoped RLS; they are hash-bound and rechecked before dispatch. Recorded publication and retrieval dates are distinct claims, neither proving current validity. Output validation requires paired risk levels or unknowns and a reason for each follow-up. Documented thinking/redacted-thinking blocks are discarded; only validated final text is saved. This supports Sonnet 5's default thinking response without exposing reasoning blocks or accepting tools. [Thinking response/configuration documentation](https://platform.claude.com/docs/en/build-with-claude/thinking).

These improvements have offline reference/mutation/mock-transport tests. They have **not** been verified with a real Sonnet 5 response. Neither model choice nor these changes activate any workspace.
