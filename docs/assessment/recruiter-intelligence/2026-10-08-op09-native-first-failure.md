# OP09 native first run: preserved failure and launcher correction

[Run 37770828265](https://github.com/cqrityjob/trust-path-recruitment/actions/runs/37770828265), job `113289696803`, tested evidence `2bb1404535fdb85e166d619901fb15c578f5bb71`, schema `9c8b8159ce5f350c6ace074c917823599d19ce99` and app `a5dd89ebee2c30f4d2ff18df7117d07e2bb125d2`. The public artifact 11547717915 ZIP was retrieved and verified against SHA256 `addc40af1a4f3ad9925f775b95ba89373abdb19b1c2487729800717bd5398073` before any change; the original failed manifest remains preserved separately.

Observed: official native PostgreSQL 17.6, GoTrue 2.194.0, Storage 1.67.20 and PostgREST 14.15 and SDK 2.110.5 passed their pins; all 387 canonical migrations applied; eight actual auto-confirmed Auth accounts and password sessions were created. Before SDK probes, journal/evidence/applications/messages/mail attempts/AI runs/erasure jobs/queue/cron were all zero, AI flags false, and the one synthetic job's receipt setting false. The SDK stage failed 78 milliseconds after setup with only fixed `OP09_NATIVE_SDK_FAILED`; application/browser/final readback were `not_run`, with no images. The owned project stopped. No 44-probe or browser acceptance is claimed.

The private SDK exception/log was not exported, so the exact original exception is unavailable. A deterministic launcher defect is independently reproduced with the installed Bun 1.3.14 and no network calls: the tracked repository `.env` contains six Supabase provider variable names, and default Bun execution loads that file before the SDK's top-level target guard. It refuses `OP09_NATIVE_INHERITED_PROVIDER_CREDENTIAL_REFUSED` before writing SDK failure details. The same harmless guard invocation accepts with `--no-env-file`. This matches the observed early failure boundary; it is an inference about that run, not recovered private exception evidence or a product/schema failure.

The bounded correction adds Bun's explicit `--no-env-file` to the SDK invocation. The browser launcher uses the already-installed Playwright Node CLI directly, avoiding the analogous Bun launcher environment ambiguity before config target validation. It does not delete/edit `.env`, unset inherited credentials to hide them, change a target/permission/44/387/browser guard, change schema or product source, or enable providers. A real inherited Supabase variable is still rejected with `--no-env-file`. Regression tests use only a temporary canary `.env`, builtin subprocesses and the existing validator; they make zero external calls. Planted controls reject removing the SDK flag or installed Node browser entry.

[Bun's primary environment-variable documentation](https://bun.com/docs/runtime/environment-variables#disabling-automatic-env-loading) documents automatic file loading and the disabling flag. The pinned local `bun 1.3.14 --help` also exposes `--no-env-file`; the regression executes that binary rather than relying on current documentation alone.

All first-run migration hashes and Auth8 setup results are actual ephemeral evidence, not hosted installation or public-runtime proof. A new exact-head native CI run must execute 44 and all four browser journeys after this correction. No local database, Docker, Auth, Storage, browser runtime or hosted service was run during diagnosis.
