# P1: versionskonflikter utan serverns transaktionsåterförsök

Schemaändring `7820076953468073c21adfa8a9d6f137e0ae8bcc`, ovanpå schema-bas `40a5f0c87a293bf692366b0bd56803d2cb843a80`. Granskat och provat 2026-10-08. Ingen appkod, typöverlagring, genererade typer, äldre tillämpad migration eller produktionsmiljö ändrades i denna leverans.

Den riktiga lokala Supabase-stacken med PostgREST 14.15 avslöjade att en avsiktlig CAS-konflikt med PostgreSQL-koden `40001` kunde återförsökas oändligt med samma gamla indata. P1:s nya ansvarig-CAS använde denna kod. Sex andra nya stale-grenar använde `check_violation`. Den omergade [P1-migrationen](../../../supabase/migrations/20270308090000_recruiter_intelligence_requirements.sql) ger nu `PT409` för samtliga sju avsiktliga P1-stale-grenar: profilversion, utbytt profil, granskningsrevision, källbindning, ansvarigversion, vald originalversion och PEACE-handoff. Domänmeddelandena `RI_STALE_VERSION`, `RI_SOURCE_STALE` och `STALE_VERSION`, funktionssignaturer, behörigheter, atomisk rollback och idempotens är bevarade. Ingen generell exception-handler konverterar databasens riktiga `serialization_failure`.

Den befintliga obligatoriska [SQL-sviten](../../../supabase/tests/recruiter_intelligence_p1_test.sql) kräver exakt SQLSTATE och exakt meddelande för dessa konfliktprov. Övriga negativa prov behåller sina tidigare kontroller. Den obligatoriska [HTTP-sviten](../../../scripts/recruiter-intelligence-p1-api-check.mjs) kräver exakt HTTP 409 / PT409/domänmeddelande; varje request har en åtta sekunders tidsgräns så en oändlig serverretry inte kan ge ett hängande eller falskt passerat prov. Den använder produktens faktiska RPC:er och en riktig PostgREST-server.

[Runnerns](../../../scripts/local-stack/run-ri-p1-evidence.sh) Dockerdefault är nu `postgrest/postgrest:v14.15`. Den mäter den startade serverns version och PostgreSQL-versionen; dessa sparas i offentliga versionsloggar och manifest. En uttrycklig image-/binär-override är fortfarande möjlig för en separat versionsjämförelse. Default ändrar enbart den isolerade verifieringen. Ingen driftmiljö uppdateras.

Den frysta omkörningen gav exit 0 på ren egen PostgreSQL 17.11 och PostgREST 14.15: hela migrationshistoriken, 93 SQL-assertioner, 23 HTTP-assertioner och åtta precisa konfliktutfall. Alla åtta var HTTP 409 / PT409; största uppmätta konfliktsvarstid var 16,46 ms. Samtidig review gav `[409,200]`, en vinnare och ett stale-avslag. Deterministiska försök med gammal ansvarigversion nekades både när valt ansvar var ändrat och när det motsvarade det nya aktuella ansvaret. Ansvarig, granskningsrevision, nästa handling och assignmentversion förblev oförändrade efter avslagen. En stale-handoff kopierade 0 källor. Oracle behöll 100 mottagna, 40 gröna/25 gula/35 grå, 27 granskade/73 återstående; datumversion V2 gav 30/35/35 och 0 aktuellt granskade. [Versionsbundet redigerat bevis](evidence/2026-10-08-p1-domain-conflicts.json) innehåller käll-/migrationshash, tjänsteversioner, konfliktsvar och logghashar. Första omkörningens äldre rapport sparades separat och skrevs inte över.

Target-/manifestproven passerade 10/10 med 39 expect-anrop; lint på ändrade JS-/TS-skript, bash syntax och git diff-kontroll gav 0 fel. Detta är schema-/SQL-/RPC-verifiering. Auth och Storage i denna runner är gateway-substitut. Appserverns egen HTTP-felkonvertering, nya browserresor, hosted installation och publicering är inte utförda här. Den separata framåtmigrationen för tillämpade P0-/legacy-CAS-funktioner ägs och verifieras av metod-/säkerhetsagenten; de äldre SQL-filerna har inte skrivits om för att få denna P1-körning att passera.

Ändringen är ännu omergad. Före installation ska den schema-PR som äger P1 ta in rättningen och köra sin obligatoriska CI, därefter tillämpas enligt befintlig schema-first releasegrind. Ingen minskad behörighetsspärr eller aktivering av AI, meddelanden, retention/cron ingår. Före merge kan den nya schemaändringen revertas med ett separat commit; efter faktisk installation kräver återställning en granskad framåtmigration och får inte beskrivas som att en tillämpad migrationsfil bara kan skrivas om.
